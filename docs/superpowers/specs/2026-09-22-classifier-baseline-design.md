# Jev Decision Lab 第二阶段：专用分类器基线设计

**日期：** 2026-09-22  
**状态：** 已完成会话设计确认，等待书面复核  
**项目位置：** `03-research/jev-decision-lab`  
**研究主题：** Jev 与专用分类器在固定 Agent 路由任务中的工程实用性比较

## 1. 背景与研究问题

Jev 的外部行为与分类器相似：输入状态和有限候选空间，输出选择及概率分布。它与 Transformer、分类器也不处在同一个概念层次。Transformer 描述模型架构，分类器描述任务形态，Jev 则是面向运行时类型化概率决策的模型产品与训练、推理接口。Jev 的内部架构尚未公开，现阶段不能证明它不是 Transformer，也不能把它简化为普通分类头。

第一阶段实验台已经支持规则、DeepSeek、Jev 和录制响应，但还不能回答一个更务实的问题：对于固定的 Agent 路由任务，专用分类器与 Jev 分别需要付出多少建设、变更和运行成本，最终能获得怎样的决策质量与效率。

第二阶段新增离线专用分类器基线，优先回答：

- 在标签稳定、任务固定时，轻量监督分类器能达到什么水平；
- Jev 或生成式模型免训练、动态定义候选空间的灵活性值多少钱；
- 标签或业务定义发生变化时，各方案需要重做哪些工作；
- 概率质量、拒答能力和高风险错误是否支持自动化；
- Jev 的价值是否主要来自准确率、校准、速度，还是更低的首次接入与变更成本。

本阶段不宣称 Jev 在模型架构上具有已被独立验证的本质创新。网站文章只陈述公开事实、本地实验事实和明确标注的推断。

## 2. 范围

### 2.1 本阶段目标

- 加入 `TF-IDF + Logistic Regression` 专用分类器；
- 保持无网络、无 API Key 的训练、推理和评估能力；
- 记录训练数据、配置、随机种子、依赖版本、产物哈希与工程成本；
- 使用现有统一 `DecisionResult` 参与准确率、校准、覆盖率、延迟与成本评估；
- 在开发集内提供按 `family_id` 分组的稳定性评估；
- 冻结后使用校准集选择阈值，并将保留测试集用于最终评估；
- 设计一次标签变化实验，显式比较重训练、规则修改和问题定义修改的成本；
- 为网站专题准备可审计、经人工审批的公开摘要。

### 2.2 非目标

- 不在当前 60 条开发样本上微调 Transformer；
- 不把交叉验证成绩写成保留测试集成绩；
- 不用复杂概率校准掩盖小校准集限制；
- 不构造单一综合分数或宣布绝对冠军；
- 不自动调用 Jev、DeepSeek 或部署网站；
- 不猜测 Jev 未公开的内部架构；
- 不执行模型选择的工具或业务动作。

小型 Transformer 分类器属于后续阶段。只有在数据规模、标签质量和实验预算足以支持微调时，才通过独立可选依赖和独立 CI 引入。

## 3. 公平性协议

比较对象完成同一个路由业务目标，但不强制采用相同学习方式。专用分类器可以使用监督训练，这是它的优势；Jev 和 DeepSeek 可以通过自然语言定义任务并零样本适配，这是它们的优势。实验比较的是总工程代价，而不是只比较一次推理输出。

| 方案 | 可使用的数据 | 允许调整的内容 |
|---|---|---|
| 规则系统 | `dev` | 关键词和规则 |
| TF-IDF 分类器 | `dev` | 特征与训练参数 |
| DeepSeek | `dev` | Prompt、标签说明和问题定义 |
| Jev | `dev` | Question、Criteria 和候选定义 |
| 所有方案 | `calibration` | 自动接受或拒答阈值 |
| 所有方案 | `test` | 仅执行冻结后的最终评估 |

正式实验禁止：

- 使用 `test` 修改规则、特征、参数、Prompt、Criteria 或阈值；
- 根据 `test` 成绩选择分类器或配置；
- 只向某一个 Provider 提供额外标签知识；
- 从准确率统计中静默删除失败请求；
- 把录制响应冒充实时模型成绩；
- 忽略分类器训练与标注成本，却只强调远程 Provider 的调用费用；
- 把开发集交叉验证与正式测试成绩混在同一排名中。

每次正式运行冻结并记录数据集 SHA-256、代码 commit、训练样本 ID、特征配置、模型参数、Prompt 或 Criteria、阈值、随机种子、依赖版本、运行环境和模型版本。

## 4. 总体架构

```text
routing-v1.yaml
      │
      ├── dev ───────────────► TF-IDF + Logistic Regression 训练
      │                              │
      │                              ▼
      │                       模型 + 训练清单 + 哈希
      │
      ├── calibration ───────► 选择拒答阈值
      │                              │
      │                              ▼
      │                         冻结实验配置
      │
      └── test ──────────────► 最终一次正式评估
                                     │
                                     ▼
                             统一 DecisionResult
                                     │
                    ┌────────────────┼────────────────┐
                    ▼                ▼                ▼
                 决策质量         概率质量         工程成本
```

新增组件：

```text
src/jev_lab/
├── training/
│   ├── features.py       # TF-IDF 特征定义
│   ├── classifier.py     # 训练、预测和模型加载
│   └── artifacts.py      # manifest、哈希和原子写入
├── providers/
│   └── classifier.py     # DecisionProvider 适配器
└── comparison.py         # 跨运行比较，不参与单次推理
```

训练逻辑与 Provider 分离。训练模块只生成可验证模型产物；Provider 只加载冻结产物并输出 `DecisionResult`。比较模块只消费已经完成的运行结果，不能改变任何预测。

## 5. 数据使用与泄漏防护

训练命令只接受 `dev`。程序必须在写入任何模型产物前验证：

- 所有训练样本的 `split` 均为 `dev`；
- 训练样本 ID 唯一；
- 数据集中每个 `family_id` 只属于一个 split；
- 四个标签均有训练样本；
- 运行时标签集合与模型标签映射完全一致。

开发稳定性采用按 `family_id` 分组的交叉验证，使同一原始意图的清晰、模糊、对抗和边界改写不会跨训练与验证折。交叉验证只用于检查模型是否极度不稳定，不参与阈值选择，也不替代正式测试。

正式流程为：

```text
全部 dev 训练
→ calibration 选择阈值
→ 冻结模型、特征、参数和阈值
→ test 最终运行
```

当前 60/20/20 的规模不足以证明普遍泛化能力。所有报告必须同时显示样本数量、合成数据属性和置信区间有限的事实。

## 6. 模型与训练产物

第一版分类器使用 scikit-learn 的 TF-IDF 与 Logistic Regression。选择它们的原因是实现透明、CPU 友好、可输出完整类别概率、无需下载预训练权重，并能够代表一个合理而非故意弱化的传统文本分类基线。

分类器依赖放入可选安装组：

```bash
pip install -e '.[classifier]'
```

默认安装和现有离线能力不依赖 scikit-learn。

每个训练目录至少包含：

```text
artifacts/<model-id>/
├── model.joblib
├── manifest.json
├── label-map.json
└── training-metrics.json
```

`manifest.json` 至少记录：

- 模型 ID 和创建时间；
- 数据集路径与 SHA-256；
- 训练样本 ID 和 `family_id`；
- 固定的训练 split；
- 标签集合与顺序；
- scikit-learn 版本；
- TF-IDF 与 Logistic Regression 参数；
- 随机种子；
- 训练耗时；
- 模型文件字节数与 SHA-256；
- Git commit。

模型加载时校验 manifest、模型哈希和标签映射。校验失败必须终止该 Provider 的运行，不能静默回退到规则系统。

## 7. CLI 与运行流程

新增命令语义：

```bash
jev-lab train --provider tfidf-logreg --split dev

jev-lab run \
  --provider tfidf-logreg \
  --model artifacts/<model-id> \
  --split calibration
```

训练命令如果收到非 `dev` split，必须在创建产物目录前失败。输出目录已存在时默认拒绝覆盖。模型运行仍通过现有 `run → evaluate → report` 流程。

推荐顺序：

```text
数据校验
→ dev 分组交叉验证
→ 全量 dev 训练
→ calibration 选择阈值
→ 冻结配置
→ test 正式运行
→ 生成完整报告和公开候选摘要
```

## 8. 指标与比较解释

### 8.1 决策质量

- Accuracy；
- 混淆矩阵；
- 每类 Precision / Recall；
- 高风险 false approval；
- Coverage 与 Selective Accuracy；
- Brier Score；
- 置信度分桶。

校准集只有 20 条，本阶段不增加 Platt Scaling 或 Isotonic Regression。它只用于选择拒答阈值。复杂校准方法必须等待更大、独立的校准数据。

### 8.2 运行效率

- 请求或本地推理成功率；
- P50 / P95 推理延迟；
- 单样本已知 API 成本；
- 训练耗时；
- 模型文件大小。

本地分类器报告 `API cost: $0`，并同时记录 CPU 环境和训练耗时，不能写成无成本。第一版不记录峰值内存，以避免平台差异较大的测量噪声。

### 8.3 建设与变更成本

记录以下可审计事实，而非伪精确的人力金额：

- 标注样本数量；
- 是否需要监督训练；
- 是否需要 API Key 或模型下载；
- Prompt、Criteria 或配置规模；
- 首次运行步骤；
- 新机器复现的网络依赖；
- 标签变化后是否需要补标、重训、重校准和重新验证。

最终报告不生成单一总分。结论按场景表述：

- 标签稳定、数据充足、高调用量：专用分类器可能更合适；
- 标签频繁变化、标注少、需要快速上线：Jev 或 LLM 可能更合适；
- 逻辑可枚举且风险高：规则系统优先；
- 需要生成、规划、解释或调用工具：分类器和 Jev 都不是完整方案。

## 9. 标签变化实验

新增独立的 `routing-change-v1` 研究场景，把 `human_review` 拆分为示例性的 `security_review` 与 `business_review`，观察每种方案面对标签变化所需的工作。

| 方案 | 必需变化 |
|---|---|
| 规则 | 修改规则并完整回归 |
| TF-IDF 分类器 | 补充新类别标注、重新训练和校准 |
| DeepSeek | 修改标签说明与 Prompt，重新校准 |
| Jev | 修改 Choice Criteria，重新校准 |

该场景与 `routing-v1` 的正式成绩分开报告。若新类别没有足够训练样本，分类器结果应明确标记为“证据不足”，而不是用少量样本制造一个看似完整的成绩。

## 10. 失败边界

以下情况必须产生明确错误，不得生成可误读的成功报告：

- 非 `dev` 数据进入训练；
- `family_id` 跨 split；
- 类别缺失或样本为空；
- 模型、manifest 或标签映射缺失；
- 模型哈希不一致；
- 依赖缺失或版本不兼容；
- 分类器概率缺少类别、越界或不归一；
- 运行配置与训练标签不一致。

推理失败仍通过现有 `RequestStatus` 和错误分类进入结果，不能把规则回退结果记在分类器名下。生产回退策略不属于本实验阶段。

## 11. 测试与 CI

实现遵循 TDD，至少覆盖：

- 训练只能使用 `dev`；
- 按 `family_id` 分组，防止交叉验证泄漏；
- 固定随机种子的可复现性；
- 非法标签、空数据和类别缺失；
- manifest 完整性与模型哈希验证；
- 标签顺序稳定；
- 损坏模型拒绝加载；
- Provider 输出完整且归一化的概率；
- 阈值只影响 Coverage 与 Selective Accuracy；
- 训练耗时不混入推理延迟；
- `train → run → evaluate → report` 离线端到端链路；
- 输出目录不被意外覆盖。

CI 增加独立 `classifier` Job：

```text
offline       现有轻量门禁，不安装分类器依赖
classifier    安装 classifier 依赖，验证训练与评估链路
```

两个 Job 都不读取 Secrets、不调用远程 Provider。任何一个 Job 失败都会阻止把该提交描述为通过验证。

## 12. 公开报告与网站专题

实验台仍只生成 `public/` 候选摘要。网站发布保留人工门：

```text
生成摘要
→ 敏感信息和证据状态检查
→ 人工审阅措辞
→ 更新 Agent 工程笔记
→ 网站验证
→ 发布
```

Jev 专题新增核心文章《Jev 与分类器到底有什么区别：从一次公平的 Agent 路由实验开始》。第一阶段先发布概念层次、公平性协议、实验设计和数据限制，并标注尚无真实 Jev 结果。第二阶段只有在真实调用完成后，才追加实测数据、失败案例、置信度分析、变更成本和宣传数字复核。

每条公开实测结论必须能够追溯到数据集哈希、代码 commit、运行 ID、Provider 与模型版本。开发集成绩、回放数据和厂商结果不得冒充独立测试结果。

## 13. 验收标准

- 默认离线流程保持可用且现有测试不回退；
- 安装 `classifier` 可选依赖后能完成训练、校准运行、评估与报告；
- 程序能够证明训练只使用 `dev` 且分组交叉验证不泄漏；
- 模型产物可验证、不可被静默覆盖或替换；
- 分类器结果进入现有统一指标而不破坏规则和远程 Provider；
- CI 的 `offline` 与 `classifier` Job 均通过；
- 报告明确区分开发稳定性、校准结果与保留测试结果；
- 网站草稿不包含未经本地真实实验支持的 Jev 性能结论。
